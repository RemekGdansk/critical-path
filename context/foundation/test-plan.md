# Test Plan

> Phased test rollout for this project. Strategy is frozen at the top (§1–§5); cookbook patterns at the bottom (§6) fill in as phases ship. Read before writing any new test.
>
> Refresh: re-run `/10x-test-plan --refresh` when stale (see §8).
>
> Last updated: 2026-10-12

## 1. Strategy

Tests follow three non-negotiable principles for this project:

1. **Cost × signal.** The cheapest test that gives a real signal for the risk wins. Do not promote to e2e because e2e "feels safer." Do not put a vision model on top of a deterministic check that already catches the regression.
2. **User concerns are first-class evidence.** Risks anchored in "the maintainer is worried about X, and the failure would surface somewhere in <area>" carry the same weight as PRD lines or hot-spot data.
3. **Risks are scenarios, not code locations.** This plan documents _what could fail_ and _why we believe it's likely_ — drawn from documents, interview, and codebase _signal_ (churn, structure, test base). It does NOT claim to know which line owns the failure. That knowledge is produced by `/10x-research` during each rollout phase. If the plan and research disagree about where the failure lives, research is the ground truth.

Expected values in every test come from an independent oracle — the PRD's worked examples, Business Logic rules and acceptance criteria, or a committed fixture — never from the output of the code under test.

Hot-spot scope used for likelihood weighting: `src/` (excluding `src/dev/`), `scripts/`, `e2e/`. 30-day churn: `src/lib/services/` 36 file-changes, `src/components/planner/` 36, `src/styles/` 8, `scripts/agent-hooks/` 8, `src/components/ui/` 5, `src/pages/` 4, `src/hooks/` 4 (20 commits).

## 6. Cookbook Patterns

How to add new tests in this project. Each sub-section is filled in once the relevant rollout phase ships; before that, the sub-section reads "TBD — see §3 Phase N."

### 6.1 Adding a domain unit test with a PRD oracle

- **Location:** colocated next to the code under test as `src/**/*.test.ts` — `.ts` only. Vitest discovers two patterns (`vitest.config.ts`): `src/**/*.test.ts`, the one Tailwind's scan excludes, and `scripts/**/*.test.ts`, for build tooling outside the Tailwind scan (§6.4); a `.test.tsx` file would be neither run nor excluded. Domain logic and its tests live in `src/lib/services/`.
- **Reference:** `src/lib/services/forecast.test.ts`, the `prdExamples` table run by the "PRD worked examples" `describe` block. To cover a new PRD rule, add one row: `rule` names the PRD source (section, user story or acceptance criterion) and doubles as the test name; `project` is built through the edit functions (or by hand only when no edit can reach the state yet); `today`, `baseDate` and both Project Finish Dates are ISO literals and `baseDateReason` is a literal reason, each one following from the PRD (the Done rows' reason does not yet; see roadmap S-07). Derive the expected dates by hand from the PRD's convention (finish = start + Duration; a successor starts on its predecessor's finish or completion date) — never with `addDays`, `forecast` or any other production helper. A row whose expected value could also be produced by a plausible bug (e.g. In Progress treated as Done) should differ from its neighbour on exactly that point. A multi-step PRD story (US-02) stays a step-by-step `it` next to the table; non-PRD edge cases go outside the "PRD worked examples" block.
- **"Today":** always injected as an ISO string (`forecast(project, today)`), never read from the clock — no `vi.useFakeTimers` or `vi.setSystemTime`. The only clock read is converted by `todayIsoDate`, tested in `src/lib/services/calendar-date.test.ts` against instants on either side of local midnight.
- **Time zone:** the whole suite runs in Europe/Warsaw (`test.env.TZ` in `vitest.config.ts`) on every machine and in both CI gates; a local-day test relies on it and must not set `process.env.TZ` itself.
- **Rendered output:** when a domain result must reach the screen correctly (e.g. no Project Finish Date while a Validation Warning exists), render the component statically from a real domain result — `renderToStaticMarkup(createElement(Component, props))` in a `.test.ts`, no DOM library, no hand-built domain objects — and assert on the text and the raw markup. Reference: `src/components/planner/ForecastSummary.test.ts`.
- **Mutation check (optional):** to see whether the new assertions would notice a changed rule, run Stryker on the lines the change touched only — `npm run test:mutation -- --mutate "path/to/file.ts:start-end"` — and review the survivors one by one in `reports/mutation/mutation.html`. Add an assertion only for a mutant that would be a user-visible or business-relevant bug; never chase the score. A score near zero is the known runner false result (§4), not weak tests; the workaround is in PROJECT_RULES "Mutation testing".
- **Run:** `npm test` (whole suite) or `npx vitest run <file>` (one file).

### 6.2 Adding a planner-state test for a rejected edit

- **When:** an edit's commit path or a view that renders from the committed project. A rule itself is tested in the domain first (`src/lib/services/project.test.ts`, §6.1); a planner-state test proves only that the state hook commits accepted edits and nothing else, and that the views follow what was committed.
- **Location:** colocated, still `.test.ts`: `src/hooks/useProject.test.ts` for the state hook, `src/components/planner/Planner.test.ts` for the planner view. Components are built with `createElement`, never JSX, as in §6.1. Each file's first line is `// @vitest-environment jsdom`, so only that file pays for jsdom and every other test stays in Node; with no `globals` in `vitest.config.ts`, each file calls `afterEach(() => { cleanup(); })` from `vitest` and `@testing-library/react` itself. No `setupFiles`, no `test.projects`.
- **No mocks:** the hook and the views run on the real domain (`@/lib/services/project`, `forecast`), never a mock of it. Fixtures are built through the real edit functions with an `accepted(...)` helper that throws on a rejection, as in `ForecastSummary.test.ts`.
- **Hook table (`renderHook`):** `rows` holds one row per edit-reachable rejection — `cycle`, the four `task-name-*` rules (via `renameTask`, and `task-name-empty` via `createTask` too), the four `project-name-*` rules, `duration-not-positive-whole-number`, `start-date-not-a-date`, and `unknown-task` through every Task-addressed action (an unknown predecessor included); each row names the hook action, the rule and a message fragment taken from the domain's wording. `start-has-predecessor` and `task-depends-on-finish` have no row: no edit can produce them, and the import table covers them (§6.3). The fixture is a small project (A → B with Durations, a START date, a project name), deep-frozen with a local `deepFreeze`, so any in-place write throws, and passed to `renderHook(() => useProject(fixture, <a Task id>))`. Each row runs the action inside `act` and asserts the rule, the fragment and none of "invalid", "conflict" or "blocked"; `result.current.project` is `toBe` the fixture (catches a rebuilt copy that would rerun the forecast and layout memos) and `toStrictEqual` a `structuredClone` taken before; `selection`, `selectedTask` (`toBe` the same Task object) and `replacements` (still `0`) are unchanged. A second `it.each` over the same rows runs the rejected action and an accepted one in one `act`, and expects the accepted edit applied to the original fixture alone (the `latest` ref); one more case runs two accepted edits in one `act` and expects them applied in sequence. `task-id-limit-reached` is a separate `it` next to the table rather than a row, since it needs a project replaced with one at the id ceiling, not the fixture. A new edit-reachable Validation Error (e.g. roadmap S-07's Done rules) adds its row here.
- **`Planner` render (`render`):** `render(createElement(Planner, { initialProject, initialSelection }))` starts from a fixture with a Task selected, so no diagram click is needed. React Flow's documented jsdom shim is applied in `beforeAll` in that file only — a `ResizeObserver` that fires once per observed element and also passes `contentRect` (React Flow 12 reads the pane's size from it, which the docs' shim omits), `DOMMatrixReadOnly` with `m22`, `HTMLElement` `offsetWidth`/`offsetHeight` read from `style` (falling back to 1), and `SVGElement.prototype.getBBox` — and `afterAll` restores every replaced property, so the shim never outlives the file even without per-file isolation. Sizing: `Planner` renders unsized, inside its own flex layout, with no test wrapper; the nodes appear and are found by their accessible names (`findByRole("button", { name: "A, 5 days" })`, "A, no Duration (Validation Warning)"). Wait for nodes with `findBy*`, never a timer.
- **Forecast in the view:** `Planner` reads the clock, so the fixture's START date is far in the future (`2999-01-01`), making the base date the START date whatever today is; no fake timers. Expected dates are hand-derived literals (A 5 days and B 3 days, independent: `2999-01-06` and `2999-01-09`). The sequence is dates → clear A's Duration (withheld: "Validation Warning" and "Forecast not possible", no "Project Finish Date" text and no ISO date anywhere in the region's markup, node warned) → restore it with a different Duration (7: `2999-01-08` and `2999-01-11`, the old dates gone), so a stale memo that replays the first forecast fails. The forecast's `role="status"` region is picked out from any other status region by its content, and its text is read with tags replaced by spaces, so a label and its value read as one phrase. Draft fields are driven with `fireEvent.change` then `fireEvent.blur`, the way the panel commits.
- **Rejected edit in the view:** a rejected Duration (`"0"`) shows a `role="alert"` naming the rule, while every committed view (the node's accessible name, the forecast's dates) still shows the previous project. Never assert that the field reverts: a rejected draft stays in the field by design. jsdom never reports `validity.badInput`, so a planner test reaches an unreadable native input by stubbing `validity` on the element and firing a key press first, so the typed-draft path is taken; the browser behaviour itself is proven in Chromium by `e2e/start-date.spec.ts`, which detects the date segment order instead of pinning a locale.
- **Render crash:** a throw while rendering the project must show the fallback, never a blank page. The fixture is a project the real domain throws on during render, built by hand because the edit functions would reject it (`cyclicProject` in `Planner.test.ts`: `forecast()` throws on its cycle), never a mock that throws, and it is passed to `Planner` as `initialProject`. `console.error` is spied and silenced with `vi.spyOn(console, "error").mockImplementation(...)`, since React and the planner both report the crash, and the spy is then asserted to have received the "Critical Path: the planner crashed while rendering." line. The download is captured by stubbing `URL.createObjectURL` (and `revokeObjectURL`, restored in `afterEach`) and `HTMLAnchorElement.prototype.click`, because jsdom has no object URLs and would navigate on the click. Assert the `role="alert"` text (the error, and the Validation Error when `validateProject` finds one, in the domain's wording with none of "invalid", "conflict" or "blocked"), the exported text with `toBe(serializeProject(project))` and the file name, and that the planner is gone (no New Task textbox). Going back to the previous project is proven at hook level (`previousProject` and `restorePreviousProject` in `useProject.test.ts`) and in the built app by `e2e/render-crash.spec.ts`, which reaches a real render throw through an imported long chain (audit A1).
- **Run:** `npx vitest run src/hooks/useProject.test.ts src/components/planner/Planner.test.ts` (both files) or `npm test` (whole suite). `vitest related` selects them for edits to `src/hooks/useProject.ts`, `src/components/planner/Planner.tsx` and the rest of `Planner`'s static import graph (§6.5, Phase 5).

### 6.3 Adding a file-format change or a new import rule

- **Location:** `src/lib/services/project-file.test.ts`, next to `src/lib/services/project-file.ts`, the only module that knows the file format; golden files live in `src/lib/services/golden/`. Import's last stage is the Project aggregate's guardian (`checkProject` in `src/lib/services/project.ts`), the same check every edit passes through. A new Validation Error rule is one entry in `TASK_CHECKS` or `PROJECT_CHECKS` in `src/lib/services/project.ts`, tested once in the `validateProject` table, plus one edit row (the hook rejection table, §6.2) and one file row when a file can hold it.
- **Golden file per shipped version or field set:** `src/lib/services/golden/project-file-0.1.json` is written by hand, never generated by the exporter, and Prettier-ignored (`.prettierignore` lists `src/lib/services/golden/`), so its bytes stay as committed. The test reads it as raw bytes (`readFileSync`), compares the import with `toStrictEqual` to a hand-written expected project (`GOLDEN_PROJECT`), checks that its Validation Warning survives, and asserts the next Task id it mints (never a deleted id).
- **Round-trip:** `expectRoundTrip(project)` exports a deep-frozen project, imports it and re-exports it: `toStrictEqual` on the project and `toBe` on the re-exported text, with no normalizer in between. `fullProject()` holds every US-03 field the model can hold today (name, START date, Durations, a cleared Duration, a deleted id); a new field gets a value in `fullProject()` or its own hand-built project, and the generated 100-Task project (`createPerfProject()`) runs through the same helper.
- **Rejection table:** `validationErrorRows` holds at least one row per `ValidationErrorRule` value (`src/lib/services/project.ts`) that a file can hold — not `task-id-limit-reached`, since the shape stage rejects a `nextTaskId` above the ceiling first ("nextTaskId must be at most …"); file-shape rows (`ProjectFileRule`: not JSON, not a project, a newer version, duplicate ids, the not-supported-yet limits) sit apart in `fileRuleRows`. Most rows are a hand edit of the hand-written `baseFile()` through `fileWith`, and `expectRejected` asserts the rule, a message fragment and that the message says none of "invalid", "conflict" or "blocked". A file that is accepted after a lossless clean-up (unsorted predecessors, untrimmed names) goes in the "normalises without loss" table instead. A new Validation Error (e.g. roadmap S-07's Done rules) adds its rows here and its edit-rule tests in the same change.
- **Lifting a not-supported-yet rejection:** roadmap S-06 lifted `day-counting-mode-not-supported-yet` (landed: the rule is gone, its rejection row is now an accepted-import and round-trip row, and `project-file-0.1-weekdays.json` holds the `weekdays` mode). S-07 lifts `task-status-not-supported-yet`: replace its rejection rows with round-trip rows and add a hand-written golden file next to the 0.1 one, named after the version and the field set (`project-file-0.1-statuses.json` with In Progress and Done Tasks and their completion dates). The version stays `"0.1"` until M-1 closes.
- **Version bump** (`"0.1"` → `"1"` when M-1 closes): the parser must still accept every shipped version, and every older golden file must still import to its hand-written project. The "is what `serializeProject` writes for that project, byte for byte" assertion moves to the new version's golden file; older golden files keep only their import assertions, so the bump does not read as a broken old-file test. A field absent from an older file gets a documented default, each with its own row — today a missing key is rejected as `file-not-a-project`, so the default applies to the older version only.
- **Browser side:** `e2e/project-file.spec.ts` exports in one browser context and imports in a fresh one, and rejects a cycle file with the current project unchanged. Add an e2e case only for behaviour no unit test reaches (the download, the file picker, the CSP).
- **Run:** `npx vitest run src/lib/services/project-file.test.ts` (the contract) or `npm run test:e2e` (the browser side, against the built app).

### 6.4 Adding a check on the built artifact

- **When:** a guarantee is a property of what the build emits, not of the configuration that asks for it. Verify the artifact, not the config: a check that compares the config with the HTML passes whenever both are loosened together, so the checker never reads `astro.config.mjs`, and no expected outcome is read from `dist/` either.
- **Oracle first:** write the rules as a numbered list from sources (PRD guardrail, PROJECT_RULES hard rule, the Risk response guidance in §2) before any code, and number violations after them. The CSP check's rules: (1) the build holds at least one HTML page — a missing `dist/` or zero pages fails; (2) every page holds exactly one `<meta http-equiv="content-security-policy">` (name and value case-insensitive), a child of `<head>` as a browser parses it; (3) no directive name appears twice; (4) `default-src`, `connect-src`, `worker-src` and `form-action` are all present, each exactly `'none'` — a worker takes its CSP from its own response, not the page's, and `form-action` does not fall back to `default-src`; (5) every source in every directive is `'self'`, `'none'`, a `'sha256-…'`/`'sha384-…'`/`'sha512-…'` hash or `data:` — host sources, `*`, other schemes, `'unsafe-inline'`, `'unsafe-eval'`, `'unsafe-hashes'`, `'strict-dynamic'`, nonces and `report-uri`/`report-to` values all fail; (6) before the meta in document order there is no `<script>`, `<base>`, `<style>` or `<noscript>` and no element with a `style` attribute (with JS off a browser parses `<noscript>` content, which can push the meta out of `<head>`), because a meta CSP governs only what is parsed after it; (7) no element other than `<a>` has a URL attribute (`src`, `href`, `srcset`, `imagesrcset`, `data`, `action`, `formaction`, `poster`) holding an absolute `http:`/`https:` or protocol-relative `//` URL. Rule 7 is deliberately stricter than its wording: it also scans `<template>` content, treats `\\`, `\/` and `/\` like `//`, checks every `srcset`/`imagesrcset` candidate, and strips tabs and newlines before matching, as URL parsing does.
- **Shape:** a pure decision module in `scripts/` — HTML strings in, violations out; no file system, no clock, no config import — next to its fixture table, and a thin CLI that reads every `*.html` under `dist/`, calls the module and turns the result into an exit code. Reference: `scripts/csp/check-page.ts` (`checkPage` for one page, `checkBuild` for the whole build) and `scripts/check-built-csp.ts`. Parse with `parse5`, so "inside `<head>`" and "before the meta" mean what a browser's tree construction makes of the page, not what a regex over the raw text sees. Node 24 runs both files directly (`node scripts/check-built-csp.ts`), so erasable TypeScript only (no `enum`, `namespace` or parameter properties), local imports with their `.ts` extension, no `@/` alias.
- **Reporting:** one violation per offending item, not one per rule, each on its own line as `<page>: rule N (short name): <directive, token or element>`, e.g. `dist/index.html: rule 5 (source allowlist): img-src allows https://x.example`; rule 1 (at least one page) has no page to name, so its single violation carries no `<page>:` prefix. Violations go to stderr with exit code 1; a pass writes `CSP check passed: <n> page(s)` to stdout. Write through `process.stdout.write`/`process.stderr.write`, so the type-checked lint needs no `no-console` exception.
- **Fixture table:** `scripts/csp/check-page.test.ts`. One helper builds a minimal page from a policy string plus optional fragments before the meta, after it and in `<body>`; every fixture is written by hand from the oracle, never copied from `dist/` and never derived from the config. Passing rows (a page shaped like the current build, an upper-case `HTTP-EQUIV`) assert an empty result. Each rejected row is named after the loosening it is (the research row letter where one applies) and lists `mentions` that one single violation must contain together — the rule number and the offending item — so an unrelated rule firing cannot pass the row. To cover a new loosening, add one row; to add a rule, add it to the oracle first, then one row per way to break it.
- **Discovery:** `vitest.config.ts` `include` lists `scripts/**/*.test.ts` beside `src/**/*.test.ts`; that widening was deliberate and verified by `npx vitest list` (lesson "Pin the build's input set"). A new location for build-tooling tests needs the same probe.
- **Gates:** a named npm script (`check:csp`), run as its own step directly after `npm run build` in `.github/workflows/ci.yml` and in the Workers Builds build command, recorded in `context/deployment/deploy-plan.md` step 7 — never a `postbuild` hook, so each gate shows the check by name. Timing rule: the dashboard command applies to every branch at once, so add a step that calls a new script only while the PR that adds the script is open and green, then merge promptly; otherwise every `main` build fails with `Missing script`. Push the red-proof commit only after the dashboard edit.
- **Red proof:** at three levels. In `npm test`, one fixture row per rule (and breaking a rule in the module turns `npm test` red). Locally, a real build after a loosening turns `npm run check:csp` red, then is reverted — once in the config and once in the output with the config unchanged (e.g. an external `<script src>` as the first child of `<head>` in `src/layouts/Layout.astro`); a missing `dist/` is red too. On the PR, a loosened commit turns `ci` (at the check's step) and `Workers Builds: critical-path` red with no preview version uploaded, and its revert turns both green.
- **Limits:** a build-time check sees only what the build emits. Serve-time injection (e.g. Cloudflare Web Analytics) stays with the manual R4 gate (deploy-plan step 5) and the P4 response check; the manual `npm run build && npx wrangler deploy` path stays unguarded, as it is for lint and tests. Rule 7 fails closed on a same-site absolute URL too (e.g. a `<link rel="canonical">` built from `site` in `astro.config.mjs` is reported as a third-party URL): keep canonical and alternate links relative, or add a reviewed exemption with its own fixture row.
- **Run:** `npm run build && npm run check:csp` (the real artifact) or `npx vitest run scripts/csp/check-page.test.ts` (the fixture table).
