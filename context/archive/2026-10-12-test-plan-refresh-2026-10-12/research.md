## Research Question

## Summary

1. **#1–#3 are mostly proven for format 0.1.** Proven: the hand-written 0.1 golden file imports to a hand-written project and is byte-identical to the exporter's output; export → import → re-export is exact (`toStrictEqual` plus byte compare, no normalizer) for 5 hand-built projects and the generated 100-Task project; `nextTaskId` never re-mints a deleted id; one rejection row exists for each of the 14 `ValidationErrorRule` values (18 rows) plus 65 file-shape rows; the built app rejects a cycle file and keeps the current project. Not proven, all because the features do not exist yet: importing an older format version once the version changes (only `"0.1"` has shipped, and the parser accepts exactly `"0.1"`), documented defaults for absent fields, round-trip of non-To-Do Statuses, completion dates and `weekdays`, and rejection rows for the PRD's Done-rule Validation Errors. These residuals belong to roadmap S-06/S-07, whose Risk lines already require a golden file each. Two minor browser-side branches are untested (file > 5 MB, file read failure). **Recommendation: mark §3 Phase 3 `complete (delivered by S-03)`** and hand the residuals to S-06/S-07, rather than keep a rollout phase open for unbuilt features.
2. **Phase 5's goal is met for domain/forecast code and vacuous for planner-state code.** The per-edit `PostToolUse` hook runs `vitest related <file> --run` on every edited JS/TS/Astro file; an edit to `forecast.ts` runs 3 test files (130 tests), but an edit to `useProject.ts`, `Planner.tsx` or `TaskPanel.tsx` finds "No test files found" and passes, because no test imports them. The mechanism needs no change: once Phase 2 adds a test that statically imports the planner-state hook, `vitest related` picks it up. The end-of-turn `Stop` hook also runs the whole unit suite and `astro check`. Caveat: the hooks are registered per machine in gitignored `.claude/settings.local.json`; `scripts/agent-hooks/hooks.json` is the template. **Recommendation: mark Phase 5 `complete`, with a note that its planner-state half activates when Phase 2 lands.**
3. **Phase 2 is still open.** No test file imports `src/hooks/useProject.ts` or any stateful planner component; no `@vitest-environment`, `renderHook`, `setSystemTime` or `useFakeTimers` appears in `src/`, `scripts/` or `e2e/`; `jsdom`, `happy-dom` and `@testing-library/react` are not installed. The e2e cycle-import spec covers the import side of "current project unchanged", not edit rejection.
4. **§4/§5/§6 hold 19 stale or partial facts** (table in Detailed Findings §4). The largest: the unit row's "7 test files … `vi.setSystemTime` controls today"; the contract row "none yet"; the AI-native row describing hooks that now exist with different behaviour; no Stryker row; the golden-file gate marked "after Phase 3" though it already runs in both gates; §6.3 still TBD; the §6.5 Phase 1 note handing clock→forecast glue to Phase 2, which `e2e/forecast-today.spec.ts` now covers. Installed versions are current except Vitest (5.0.3 installed, 5.0.4 published). The Stryker Vitest-runner false result still applies: 10.0.0 is the latest runner on npm (published 2026-08-14), and the installed runner still joins names with `' '`.

### 2. §3 Phase 5 against `scripts/agent-hooks/`

Phase 5 goal (`test-plan.md:57`): "Run the related domain and state tests when an agent edits forecast or planner-state code".

- **Per edit:** `PostToolUse` on `Write|Edit` runs `lint-edited-file.ts` and `related-tests.ts` (`scripts/agent-hooks/hooks.json:14-29`). `related-tests.ts` runs `vitest related <file> --run` with a 50 s budget under a 60 s hook timeout and blocks with exit 2 on failure (`related-tests.ts:6-9`). It fires for any file matching `LINTED` (`.ts/.tsx/.js/.astro` …, `hook-lib.ts:14`), not only forecast/state files.
- **Probe on this commit** (`npx vitest related <file> --run`):
  - `src/lib/services/forecast.ts` → 3 files, 130 tests (`forecast.test.ts`, `project-file.test.ts`, `ForecastSummary.test.ts`)
  - `src/lib/services/project.ts` → 7 files, 229 tests, ~1 s wall time
  - `src/components/planner/ForecastSummary.tsx` → 1 file, 2 tests
  - `src/hooks/useProject.ts`, `src/components/planner/Planner.tsx`, `src/components/planner/TaskPanel.tsx` → "No test files found, exiting with code 0"
- Context7 (Vitest v5.0.3 CLI docs): `vitest related` "Run only tests that cover a list of source files. Works with static imports … but not the dynamic ones". So a future hook-level test that statically imports `useProject` will be selected with no hook change.
- **End of turn:** `Stop` runs ESLint on changed files, the whole `vitest run`, `astro check`, and the agent-hook tests when `scripts/agent-hooks/` changed (`end-of-turn.ts:34-52`), measured against a turn-start baseline (`hook-lib.ts:125-143`, `:196-201`), with one retry (`end-of-turn.ts:15-17`).
- **Proof of the hooks:** `npm run test:hooks` — 56 tests, all passing on this commit (12 per-edit lint, 12 per-edit related-tests, 12 end-of-turn, 6 turn baseline, 2 plumbing, 12 hook config). Excluded from `npm test` (`vitest.config.ts:8-11`); PROJECT_RULES.md:28 says never a CI or deploy gate.
- **Registration:** per machine. `hook-lib.ts:1-3`: "hooks.json is the hook config to merge into .claude/settings.local.json (gitignored, per machine)". This machine's `.claude/settings.local.json` holds the same three events; `.claude/` is gitignored (`.gitignore:1`); the committed `.claude/settings.json` has no hooks.

Verdict: the goal is met for domain and forecast code; for planner-state code it is met in mechanism but checks nothing until Phase 2 supplies a test. §4's "When NOT to use: UI-only or styling edits, or when the related tests take longer than a few seconds" (`test-plan.md:71`) does not describe the implementation: the hook runs on UI edits too (cheaply, with no related test found), and its budget is 50 s, not "a few seconds".
